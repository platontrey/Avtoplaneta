## 1. Золотой протокол сеньор-разработчика: Агент обязан спрашивать пользователя

Агент никогда не принимает скрытых архитектурных решений. Агент мыслит системно и **ОБЯЗАН остановить работу и спросить пользователя**, если возникает развилка:

### 1.1. Триггеры для обязательного вопроса пользователю:
1. **Выбор механизма коммуникации:** синхронный gRPC vs брокер (Redis Streams) vs in-process Go concurrency (goroutines/channels).
2. **Изменения схемы БД (DDL):** новые таблицы, внешние ключи, составные индексы, добавление колонок с дефолтами, смена статусов.
3. **Фоновая обработка:** in-process воркер (Go ticker) vs Transactional Outbox + Redis Streams.
4. **Контракты API:** добавление или изменение RPC методов, proto-полей, ломающие изменения в DTO или маршрутах.
5. **Стратегия отказоустойчивости (Fault Tolerance):** поведение при падении внешних сервисов (Elasticsearch, соседние микросервисы) — fallback в PostgreSQL, кэш или ошибка.

### 1.2. Формат вопроса пользователю:
- **Суть задачи и архитектурный контекст.**
- **Вариант 1 (Рекомендуемый сеньором):** почему это оптимально, какие плюсы и компромиссы.
- **Вариант 2 (Альтернативный):** альтернатива и почему она уступает.
- **Четкий вопрос к пользователю на подтверждение.**

## 2. Матрица стандартных решений под стек (Senior Default Matrix)

| Задача | Стандартное решение (Default) | Обоснование |
| :--- | :--- | :--- |
| **Параллельная работа внутри одного сервиса** (сжатие фото, парсинг Excel, fan-out I/O) | **Стандартные инструменты Go** (`errgroup.WithContext`, семафор на каналах `chan struct{}`, горутины) | Нулевые накладные расходы, изоляция внутри процесса, управление через `context.Context`. |
| **Синхронный межсервисный вызов** (списание детали при заказе, получение профилей) | **gRPC (Protobuf)** | Строгая типизация, минимальный оверхед, гарантированная Strong Consistency. |
| **Асинхронные события между сервисами** (`seller_renamed`, уведомления, аудит) | **Redis Streams** (`XADD`, Consumer Groups `XREADGROUP`, `XACK`, `XAUTOCLAIM`) | Декаплинг сервисов, устойчивость к сбоям, горизонтальное масштабирование воркеров. |
| **Гарантированная отправка событий из БД без потери (No Dual-Write)** | **Transactional Outbox Pattern** (`outbox_events` + PostgreSQL `LISTEN/NOTIFY` + Dispatcher) | Атомарность в единой транзакции с бизнес-данными, мгновенная реакция по `pg_notify`. |
| **Полнотекстовый поиск запчастей, опечатки, фасеты** | **Elasticsearch** (русский стеммер, синонимы `synonyms.txt`) | PostgreSQL медленно и неэффективно ищет по нечетким запросам запчастей. |
| **Хранение данных и транзакции** | **PostgreSQL** (`Database-per-Service`, `sqlc`, `pgx/v5`) | Строгие ACID транзакции, реляционная целостность, отсутствие тяжелых ORM. |
| **Кэш и быстрые ответы** | **Redis кэш + ETag / `If-None-Match`** | Снижение нагрузки на БД/ES, моментальный ответ `304 Not Modified`. |

## 3. База данных: Миграции, sqlc и pgx/v5

1. **Правило размещения миграций (Go embed):**
   - Новая миграция `0000XX_name.up.sql` и `.down.sql` создается **ОДНОВРЕМЕННО** в двух папках:
     - `backend/<service>/db/migrations/` (для генератора `sqlc`).
     - `backend/<service>/internal/repository/migrations/` (для раннера `//go:embed`).
2. **Безопасность миграций:** Использовать `IF NOT EXISTS` / `IF EXISTS`, безопасные `DEFAULT` для `NOT NULL` полей, обязательный `.down.sql`.
3. **sqlc:** Запросы в `db/queries/*.sql`. Использовать явные аргументы `sqlc.arg(name)` / `sqlc.narg(name)`. После правок запускать `sqlc generate`.
4. **pgx/v5:** Пул `*pgxpool.Pool`. Использовать `pgx.Batch` для пакетных вставок (никаких циклов `INSERT`!). Для очередей — `FOR UPDATE SKIP LOCKED`.

## 4. Elasticsearch: Архитектура поиска и CQRS

1. **PostgreSQL — единственный Source of Truth.** Elasticsearch — читающая проекция (CQRS read-model).
2. **Синхронизация:** Строго через Transactional Outbox (никакого Dual-Write напрямую из HTTP-хэндлера).
3. **Отказоустойчивость:** Если Elasticsearch недоступен, сервис логирует `Warn` и переключается на fallback-поиск через PostgreSQL (`ILIKE`), не аварийно завершая работу.
4. **Фильтрация:** В любых поисковых запросах обязателен фильтр `quantity >= 0`.

## 5. Критические доменные инварианты

- **Семантика поля `quantity`:**
  - `quantity > 0`: в наличии на складе.
  - `quantity == 0`: дефектные ведомости / спецпозиции. **ОБЯЗАНЫ ОСТАВАТЬСЯ ВИДИМЫМИ** в поиске, UI и XML-выгрузках.
  - `quantity == -1`: полностью списанные/проданные детали через `orders-service`. Маркер сокрытия из выдачи.
  - **Правило SQL/ES:** ВСЕГДА использовать `WHERE quantity >= 0`. Запрещено писать `> 0`.
- **Идемпотентность списаний:** Учет в таблице `part_stock_operations`.
- **CRM и дедупликация:** Нормализация `parseBuyerInfo(raw)` к `+7XXXXXXXXXX`, уникальный индекс `idx_customers_unique_phone`, `409 Conflict` на дубликаты.
