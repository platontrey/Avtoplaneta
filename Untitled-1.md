## Короткое резюме
Avtoplaneta — комплексная система управления автозапчастями: веб-интерфейс (PWA), Android-приложение и backend на Go в виде микросервисов с API Gateway, поиском, мониторингом и продакшен-развертыванием через Docker + Traefik.

- Формат разработки: **весь проект сделан мной в одиночку** (архитектура, код, инфраструктура, мониторинг, безопасность, сборка/деплой).
- Доменная область: **инвентарь запчастей, заказы, пользователи и роли, поиск, аналитика/статистика, сообщения/чат, AI-помощник**.
- Акцент: производительность UI (INP), безопасность (CSRF, cookie-based auth, CSP), наблюдаемость (Prometheus/Grafana), устойчивость (rate limiting, circuit breaker, bulkhead).

## Что умеет система (функциональность)
### Пользователи и доступ
- Локальный логин + **Google OAuth**.
- Роли: **admin / manager / operator**.
- Cookie-based сессии, защищенные middleware на gateway и сервисах.

### Инвентарь запчастей
- CRUD запчастей, статусы, атрибуты (бренд/модель/локация/категория и т.д.).
- Загрузка и хранение изображений (uploads), проксирование через gateway.
- **Поиск**: полнотекстовый + фильтры через Elasticsearch (с fallback/параллельной поддержкой БД-логики где нужно).

### Заказы
- Создание/просмотр/обновление статусов.
- Цветовые статусы (red/brown/yellow/green) + текстовое описание.

### Аналитика и мониторинг
- Статистика (например: распределение по категориям, стоимость).
- Prometheus метрики во всех сервисах + Grafana dashboard.

### Messaging / чат
- Выделенный сервис сообщений, хранение данных, интеграции, метрики.

### AI-помощник
- Интеграция с **OpenRouter** (модель по умолчанию: `x-ai/grok-4.1-fast:free`).
- Fallback: rule-based логика команд, если API ключ отсутствует/недоступен.
- Формат ответа: JSON с action (navigate/search/add/update/delete).

## Архитектура (как устроено)
### Компоненты
- **Frontend**: React + TypeScript + Vite + Tailwind (PWA).
- **Android**: Java/Kotlin (Hilt/Room/Retrofit/OkHttp).
- **Backend**: Go микросервисы:
  - API Gateway (8080)
  - Auth Service (8083)
  - Parts Service (8081)
  - Orders Service (8082)
  - Messaging Service (8084)
- **Инфраструктура**:
  - Docker Compose
  - Traefik (reverse proxy, SSL Let’s Encrypt)
  - Nginx (раздача фронта)
  - PostgreSQL, Redis, Elasticsearch
  - Prometheus + Grafana

### Почему микросервисы (а не монолит)
- Разные домены (auth / parts / orders / messaging) с независимыми нагрузочными профилями.
- Возможность независимого масштабирования и изоляции ошибок.
- Четкие границы ответственности, проще развивать функциональность блоками.

### Почему API Gateway
- Единая точка входа для Web/Android.
- Централизация: CORS, security headers, rate limiting, метрики, проксирование.
- Сокрытие внутренней топологии сервисов, удобная маршрутизация.

## Технологии проекта (полный список) + почему использовались

## 1) Web Frontend (веб-приложение / PWA)
### React + TypeScript
- Почему React:
  - Быстро строить сложный UI (формы, таблицы, модалки, фильтры).
  - Большая экосистема UI/хуков/роутинга.
- Почему TypeScript:
  - Контроль типов для моделей API (запчасти/заказы/пользователи).
  - Упрощает рефакторинг и снижает количество runtime-ошибок.

### Vite
- Почему:
  - Быстрый dev-server, HMR.
  - Хорошая сборка и контроль чанков.
  - Удобная интеграция PWA (Workbox) и прокси на backend.

### Tailwind CSS (+ tailwind-merge, clsx, class-variance-authority)
- Почему:
  - Быстрый UI-итеративный дизайн без долгих правок CSS-файлов.
  - Легко поддерживать единый стиль и масштабировать компоненты.
  - `tailwind-merge`/`clsx` — безопасная композиция классов.

### Radix UI
- Почему:
  - Доступные (a11y) примитивы: Dialog, Select, Tabs, Tooltip и т.п.
  - Контроль поведения и стилей, удобно комбинировать с Tailwind.

### TanStack React Query
- Почему:
  - Кэширование, дедупликация запросов, инвалидация, управление состоянием загрузки/ошибок.
  - Стабильный UX (например, списки запчастей/заказов без “дребезга” UI).

### React Router
- Почему:
  - Маршрутизация, защищенные роуты, удобная навигация между разделами.

### Формы и валидация: react-hook-form + zod (+ @hookform/resolvers)
- Почему:
  - Быстрые формы без лишних перерендеров.
  - Схемная валидация, единые правила и сообщения об ошибках.

### UI/визуализация
- Recharts:
  - Графики статистики (перцентиль/распределения/динамика).
- Framer Motion / Motion:
  - Контролируемые анимации для UX (при этом оптимизировал тяжелые hover/tap эффекты ради INP).
- Lucide React:
  - Единый и легкий набор иконок.

### Безопасность в UI
- DOMPurify:
  - Защита от XSS при отображении потенциально “грязных” данных (если такие места появляются).

### Производительность
- `manualChunks` в Vite:
  - Разнос vendor/ui/query/forms/utils для стабильного кеширования и меньшего initial bundle.
- Оптимизация INP:
  - Убирал тяжелые анимации, оптимизировал загрузку изображений, применял debounce поиска.

### PWA (vite-plugin-pwa + Workbox)
- Почему:
  - Установка “как приложение”.
  - Offline/кэширование ресурсов и более быстрые повторные открытия.
  - Быстрый доступ через shortcuts (например: “Добавить запчасть”, “Инвентарь”).

## 2) Backend (Go микросервисы)
### Go
- Почему:
  - Высокая производительность и низкое потребление ресурсов.
  - Хорошая модель конкурентности (goroutines), удобно для I/O (БД/Redis/HTTP).
  - Простая сборка в один бинарник, удобно деплоить в контейнерах.

### Gin
- Почему:
  - Быстрый HTTP framework, удобные middleware.
  - Простое построение REST API и прокси в gateway.

### GORM
- Почему:
  - Быстрое моделирование сущностей и миграций.
  - Упрощение CRUD, ассоциаций, транзакций.
- Где дополнял:
  - Для сложных запросов/динамики использовал query builder (например, Squirrel).

### PostgreSQL
- Почему:
  - Надежная реляционная БД: транзакции, индексы, целостность.
  - Хорошо подходит под сущности “заказы/позиции/пользователи/запчасти”.

### Redis
- Почему:
  - Быстрый кэш и хранилище краткоживущих данных.
  - Подходит под rate limiting / кэширование / сессии/CSRF (в продакшене).
  - Снижение нагрузки на БД и ускорение типовых операций.

### Elasticsearch
- Почему:
  - Полнотекстовый поиск по названиям/описаниям, фильтры, релевантность.
  - Лучше масштабируется под “поисковые” запросы, чем SQL LIKE/ILIKE на больших объемах.
  - Поддержка fuzzy/boost-поиска.

### Auth: Gorilla Sessions + Goth (Google OAuth) + bcrypt (golang.org/x/crypto)
- Почему cookie-based sessions:
  - Простая и безопасная модель для web (HttpOnly, SameSite, Secure).
  - Не нужно хранить токены на клиенте.
- Почему Goth:
  - Готовая интеграция OAuth провайдеров (Google), меньше ручной работы и ошибок.
- Почему bcrypt:
  - Надежный hashing паролей (salt + cost), стандарт для password storage.

### API документация
- swaggo/gin-swagger + swagger files:
  - Почему:
    - Быстрая генерация swagger UI, удобство для тестирования и демонстрации API.

### Наблюдаемость
- prometheus/client_golang:
  - Почему:
    - Стандарт де-факто, совместимость с Grafana.
    - Метрики latency/throughput/errors для диагностики проблем.

### Логирование
- logrus:
  - Почему:
    - Структурированные логи, удобно фильтровать по полям.
    - Единый подход по сервисам.

### Устойчивость и защита (gateway)
- Circuit Breaker (go-resiliency/breaker):
  - Почему:
    - Быстро “отключать” проблемный сервис и не выжигать ресурсы повторными попытками.
- Retrier (go-resiliency/retrier):
  - Почему:
    - Автовосстановление при временных сетевых сбоях.
- Rate limiting (x/time/rate):
  - Почему:
    - Защита от злоупотребления и случайной перегрузки (в том числе от UI багов).
- Bulkhead (semaphore channels):
  - Почему:
    - Ограничение параллелизма на сервис → изоляция очередей и стабилизация latency.

### Безопасность (gateway + сервисы)
- CORS allowlist:
  - Почему:
    - Разрешать только доверенные origins (localhost, dev-hosts, домен).
- Security headers:
  - CSP, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy:
  - Почему:
    - Снижение класса web-атак (XSS/clickjacking/MIME sniffing и т.д.).
- CSRF:
  - Почему:
    - При cookie-based auth защита CSRF обязательна для state-changing запросов.
- Ролевой доступ:
  - Почему:
    - Контроль функционала на уровне backend, не доверять только UI.

## Ключевые инженерные решения (и почему так)
### 1) Cookie-based auth вместо JWT
- Плюсы:
  - Токен не хранится в localStorage → ниже риск XSS-кражи.
  - HttpOnly cookies, SameSite → проще сделать безопасно.
- Минусы:
  - Нужно правильно делать CSRF и настройки CORS/credentials.
- Что сделал:
  - CSRF токены + middleware; allow credentials; строгие заголовки.

### 2) Elasticsearch для поиска
- Плюсы:
  - Реальный полнотекстовый поиск, релевантность, fuzziness, фильтры.
- Минусы:
  - Сложнее инфраструктура (еще один сервис), синхронизация индекса.
- Что сделал:
  - Индексация данных и поиск с фильтрами, продуманные поля text/keyword.

### 3) Устойчивость в gateway (circuit breaker / retry / bulkhead / rate limit)
- Зачем:
  - В микросервисах сбои неизбежны; gateway должен ограничивать “цепную реакцию”.
- Эффект:
  - Стабильнее latency, меньше лавинообразных таймаутов, сервисы проще “вытягиваются” после ошибок.

### 4) Наблюдаемость по умолчанию
- Зачем:
  - Любая продакшен-система должна отвечать на вопросы “почему медленно?” и “почему падает?”.
- Что сделал:
  - Унифицированные метрики по HTTP, плюс бизнес-метрики в messaging.

### 5) PWA и оптимизация производительности UI
- Зачем:
  - Быстрый UX на слабых устройствах, “почти как нативное приложение”.
- Что сделал:
  - Разнос чанков, оптимизация анимаций, параллельная работа с изображениями, debounce поиска.

## A. Архитектура и system design

### 1) Почему выбрал микросервисы?
- Потому что домены независимые: auth, заказы, инвентарь, сообщения. У каждого разная нагрузка и темп изменений.
- Можно масштабировать parts отдельно от auth, изолировать ошибки и упростить владение кодом.
- Для pet-проекта это сложнее, но я сознательно “тренировал продакшен-подход”: gateway, метрики, деплой, безопасность.

### 2) Что делает API Gateway и почему не ходить напрямую в сервисы?
- Gateway — единая точка входа: CORS, security headers, логирование, метрики, rate limiting, маршрутизация.
- Клиентам не нужно знать топологию сервисов и порты.
- В проде это упрощает SSL, домены и политки доступа.

### 3) Как устроено взаимодействие сервисов?
- Входящие запросы приходят в gateway, дальше проксируются в нужный сервис по префиксам (`/auth`, `/api/inventory`, `/orders`, `/api/messaging`, `/uploads`).
- Общие cross-cutting concerns находятся в gateway, доменная логика — в сервисах.

### 4) Как масштабировать систему?
- Горизонтально масштабировать stateless сервисы (gateway, parts, orders, messaging).
- Redis/Postgres/Elasticsearch — отдельные компоненты, их масштабирование отдельно (репликация/кластеризация при необходимости).
- Traefik балансирует трафик на несколько экземпляров сервисов.

### 5) Где могут быть узкие места?
- Поиск: Elasticsearch при больших индексах/сложных запросах.
- База: PostgreSQL при тяжелых join/индексах/блокировках.
- Uploads: изображения (I/O и сеть).
- Gateway: если он делает слишком много работы (поэтому нужны лимиты/метрики и иногда вынос логики обратно в сервисы).

### 6) Какие SLA/метрики важны?
- 95p latency по ключевым endpoints.
- Error rate (4xx/5xx) и их распределение по маршрутам.
- Throughput (RPS) в часы пик.
- DB: пул соединений/ошибки/медленные запросы.
- Search: latency и ошибки запросов в ES.

## B. Безопасность

### 7) Как реализована аутентификация?
- Cookie-based сессии (HttpOnly cookies).
- Auth-service отвечает за логин/OAuth и создание сессии.
- Gateway проверяет сессию middleware и роли на защищенных маршрутах.

### 8) Почему при cookie-based auth нужна CSRF защита?
- Потому что браузер автоматически прикрепляет cookies к запросам.
- Без CSRF злоумышленник может заставить пользователя выполнить state-changing запрос.
- Поэтому я добавил CSRF токены и требование `X-CSRF-Token` на опасных операциях.

### 9) Как настроить CORS безопасно?
- Разрешать только конкретные origins (allowlist), включать `AllowCredentials`.
- Не использовать `*` для origins при credentials.
- Я явно перечисляю dev/prod origins и ограничиваю заголовки/методы.

### 10) Зачем CSP и другие security headers?
- CSP снижает риск XSS, ограничивает источники скриптов/стилей/соединений.
- X-Frame-Options защищает от clickjacking.
- nosniff снижает риск MIME sniffing атак.
- Referrer-Policy/Permissions-Policy уменьшают утечки и доступ к опасным API.

### 11) Как хранишь пароли?
- Только как bcrypt-хэши, никогда в plaintext.
- При проверке — compare hash.
- Cost можно регулировать под нагрузку.

### 12) Что с rate limiting?
- На gateway стоит лимит запросов на сервис/класс маршрутов.
- Это защищает от brute-force на логин и от случайной перегрузки.

### 13) Что бы улучшил в security, если делать “боевой” прод?
- Централизованный секрет-менеджмент (Vault/SSM), ротация ключей.
- Более строгий CSP (без unsafe-inline/unsafe-eval в prod).
- WAF/бот-защита на периметре.
- Audit log (кто/когда изменил запчасть/заказ) с неизменяемым хранением.
- mTLS внутри кластера или service mesh (если инфраструктура позволяет).

## C. Go backend (практика)

### 14) Почему Gin?
- Низкий overhead, удобные middleware.
- Быстро поднять REST API и прокси-логику в gateway.

### 15) Как реализовал graceful shutdown?
- В gateway/main используется контекст с cancel и обработка SIGINT/SIGTERM.
- Сервис корректно завершает работу, не обрывая запросы резко.

### 16) Что такое circuit breaker и зачем он тебе?
- Паттерн устойчивости: если сервис начинает часто ошибаться, “размыкаем цепь” и быстро возвращаем ошибку, вместо таймаутов.
- Это снижает нагрузку, ускоряет деградацию и дает сервису восстановиться.

### 17) Когда retry полезен, а когда вреден?
- Полезен при временных сетевых сбоях/5xx.
- Вреден при системных ошибках (валидатор/400) и при перегрузке (может добить систему).
- Поэтому retry должен быть ограничен и наблюдаем.

### 18) Зачем bulkhead (ограничение параллельности)?
- Чтобы один проблемный маршрут/сервис не “съел” все goroutines/соединения.
- Это стабилизирует p95 latency и защищает систему от каскадных отказов.

### 19) Как организована обработка ошибок?
- Нормализованные ошибки на HTTP-уровне (коды, сообщения).
- Логирование ошибок с контекстом (endpoint, ip, статус, поля).

### 20) Как тестировал?
- Есть unit/integration тесты в сервисах (например, repository/service/handlers тесты).
- Для “боевого” качества добавил бы контрактные тесты между gateway и сервисами + e2e через docker-compose.

## D. База данных и данные

### 21) Почему PostgreSQL?
- Транзакции и целостность важны для заказов/позиций.
- Индексы и запросы гибче, чем в NoSQL для этого домена.

### 22) Как бы проектировал индексы?
- По частым фильтрам: category/brand/model/location/status.
- Для заказов: seller/status/created_at.
- Для полнотекста не мучаю SQL → отдаю поиск Elasticsearch.

### 23) Как решать проблему N+1?
- В GORM — preload ассоциаций там, где это нужно.
- Либо плоские запросы/джойны для списков, если preload дает лишнюю нагрузку.

### 24) Какие типичные проблемы с ORM?
- Скрытые запросы, N+1, неочевидные транзакции, сложные запросы неудобны.
- Поэтому иногда добавляю query builder (Squirrel) или сырой SQL в “горячих” местах.

## E. Elasticsearch

### 25) Как синхронизируешь данные БД и индекс?
- Базовый подход: после CRUD в parts-service обновлять/удалять документ в ES.
- Для надежности в продакшене добавил бы:
  - outbox pattern + фонового консьюмера
  - периодическую reindex задачу
  - idempotent обновления

### 26) Что такое keyword vs text?
- `text` — для полнотекста (анализатор, токены).
- `keyword` — для точных фильтров/агрегаций/сортировки.
- Поэтому поля типа category/brand/model лучше иметь как keyword (или multi-field).

### 27) Как бороться с опечатками?
- fuzziness, ngram анализатор, или отдельные поля для autocomplete.
- В проекте использую “fuzzy + boost” подход: приоритет названию, допуск опечаток.

### 28) Какие метрики снимаешь?
- Счетчик запросов по method/endpoint/status.
- Гистограмма времени ответа (duration_seconds).

- Смотрю p95 latency — где деградация.
- Коррелирую с логами по request-id/временному окну.
- Проверяю зависимости (Postgres/Redis/Elasticsearch) по health/ошибкам.

### 30) Что бы добавил дальше?
- Трейсинг (OpenTelemetry end-to-end).

- SLO и алерты (HighErrorRate, HighLatency).

## G. Frontend (React)

### 31) Почему React Query, а не Redux для серверного состояния?
- Серверное состояние — это кэш запросов + инвалидации.
- React Query решает это из коробки: refetch, retries (на клиенте осторожно), stale time, dedupe.
- Redux оставил бы под UI state (если он сложный и глобальный).

### 32) Как избежал “дребезга” запросов при поиске?
- Debounce ввода.
- Кэширование результатов по query ключу.
- Инвалидация только там, где нужно.

### 33) Почему Tailwind + Radix?
- Tailwind ускоряет разработку интерфейса.
- Radix дает доступные компоненты и корректную клавиатурную навигацию.
- Вместе получается “быстро + качественно”.

### 34) Почему сделал PWA?
- Для бизнес-приложения удобно: быстро открывается, можно установить, работает стабильнее в мобильных браузерах.
- Плюс кэширование снижает повторные загрузки.

### 35) Как работал с производительностью (INP)?
- Убирал тяжелые анимации на интерактивных компонентах.
- Делал более предсказуемую работу с изображениями (параллельная загрузка, оптимизация рендера).
- Разносил чанки, чтобы initial load был легче.

### 36) Как бы улучшил фронт еще?
- Виртуализация длинных списков инвентаря (react-virtual).
- RUM метрики (web-vitals) с отправкой в мониторинг.
- Оптимизация изображений: webp/avif, server-side resizing.

## I. DevOps / Deploy

### 41) Почему Traefik?
- Авто SSL, простая конфигурация маршрутов через labels.
- Удобно в docker-compose сценарии.
- Dashboard для диагностики роутинга.

### 42) Как настроены healthchecks?
- Для gateway: `/health`.
- Для сервисов и инфраструктуры: проверки readiness/health на уровне контейнеров.
- Это помогает оркестрации (даже в compose) и упрощает диагностику “почему не стартует”.

### 43) Чем отличается dev и prod compose?
- В dev:
  - Монтируются исходники (volumes).
  - Команды `go run` / `npm run dev`.
  - Быстрая итерация.
- В prod:
  - Собранные образы (multi-stage build).
  - Nginx раздает статику.
  - Traefik с TLS и certresolver.

### 44) Что бы добавил для настоящего CI/CD?
- Сборка образов в registry.
- Автотесты + линтеры (Go test, ESLint, возможно e2e).
- Автодеплой на сервер (SSH/Ansible) или Kubernetes.
- Миграции БД как отдельный шаг.
